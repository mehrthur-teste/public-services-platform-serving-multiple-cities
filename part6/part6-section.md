# Part 6 – Recommend Specialized Database Models

| Data Category | Why a Basic Relational Table Needs Extension or Organisation | Recommended Model or Approach | Queries or Operations Supported | Contribution to Platform Goals | Limitation or Risk |
| --- | --- | --- | --- | --- | --- |
| Spatial location data | Separate latitude/longitude values do not provide geometry types, coordinate-system handling or indexed spatial relationships. | PostgreSQL with PostGIS; point, line and polygon geometries; GiST spatial indexes. | Facilities within a distance; roads intersecting zones; point-in-zone searches. | Locate incidents, select nearby facilities and coordinate services geographically. | Invalid geometries, inconsistent coordinate systems or unsuitable query expressions can produce incorrect or slow results. |
| Multimedia evidence | Tables can hold binary data, but storing large file contents with transactional records does not provide the chosen object-storage delivery and lifecycle approach. | S3 object storage plus PostgreSQL media metadata and evidence-link tables. | Upload/retrieve an object; search evidence by request, inspection or capture ID; verify checksum and availability. | Keep evidence accessible and traceable without enlarging operational tables with file contents. | Uploads and metadata updates can fail independently; access, retention and reference reconciliation must be coordinated. |
| Time-series or temporal sensor data | A relational table can store timestamps, but continuous ingestion requires suitable time organisation, bounded queries and duplicate handling. | MongoDB time-series collections for environmental readings; PostgreSQL sensor/time indexes for transportation. Evaluate time partitioning if volume warrants it. | Device readings over a period; metric/unit aggregates; traffic trends and transit-arrival comparisons. | Support monitoring and provide temporal observations for alerts and planning. | Late or repeated observations distort results; MongoDB time-series updates are restricted and cross-store snapshots may differ. |
| Hierarchical or semi-structured service requests | A flat request row cannot express department ancestry by itself; variable fields need a deliberate schema and validation policy. | Normalised PostgreSQL requests and a self-referencing department hierarchy. Recursive SQL traverses it; JSONB is an optional extension for justified variable attributes. | Find descendant departments; list their assigned requests; retrieve status history; optionally filter validated JSONB attributes. | Preserve accountable ownership and allow variation without abandoning relational integrity. | Cycles and deep recursion need control. Optional JSONB requires field validation and an explicit schema migration. |
| Active database behaviour | Ordinary stored rows do not automatically execute a response when another row changes. | PostgreSQL event-condition-action triggers for local validation and invariants; proposed outbox/worker for asynchronous notifications if required. | On INSERT/UPDATE, validate camera type, department hierarchy or work-order completion; reject invalid changes within the transaction. | Apply shared local rules consistently across write paths. | Expensive or cascading triggers add latency and hidden coupling. Asynchronous notifications require retries and delivery monitoring. |
| Rule-based emergency response logic | Storing a threshold is insufficient to select an effective policy, evaluate an event and govern response actions. | An external rule-evaluation service; approved versioned JSONB conditions in PostgreSQL; alerts linked to exact rule versions. | Select active/effective rules; evaluate an observation; deduplicate alerts; record acknowledgement and escalation. | Make emergency decisions traceable and reproducible under approved policies. | Conflicting rules, stale versions, event bursts or repeated delivery require governance, retries and idempotency. |
| Historical planning data | Operational tables can answer reports, but repeated broad joins compete with service activity and lack a shared analytical grain. | A dimensional star-schema approach in a separate PostgreSQL analytical database; date/city/facility dimensions and daily facts. | Compare cities and periods; aggregate traffic, environmental metrics, service performance and maintenance cost. | Provide consistent planning indicators while managing reporting separately from operations. | Refresh lag and inconsistent units or grains can mislead. Separate databases still share resources if deployed on the same server. |

## Justification of Specialized Database Approaches

We recommend specialised approaches for all seven categories while retaining the Part 2 architecture. Relational storage remains appropriate for accountable operational records; extensions and complementary models address geometry, files, time, hierarchy, automatic reactions, governed rules and analytical summaries. Elmasri and Navathe (2016) provide the conceptual foundation for distinguishing these advanced models. The following recommendations apply those concepts to the platform’s actual access patterns.

Spatial locations require more than untyped coordinate columns. PostGIS adds geometries and spatial operations to PostgreSQL, enabling distance, intersection and containment queries. Index-aware operations can use GiST indexes to reduce candidate comparisons (PostGIS Project, n.d.-a). This supports incident localisation and service-zone coordination. Valid geometries, consistent coordinate systems and appropriate distance units remain essential; otherwise, even a fast query can return misleading results.

Multimedia uses S3 for object contents and PostgreSQL for searchable metadata and business links. Large files remain outside operational tables, while identifiers connect evidence to requests, inspections and captures. Object retrieval and lifecycle management support this separation (Amazon Web Services, n.d.-d). However, a database change and file transfer can fail independently. Pending states, verification and reconciliation therefore remain necessary. This illustrates the integration and partial-failure concerns discussed by Kleppmann (2017), which motivate explicit recovery when a workflow spans independent stores.

Temporal observations require deliberate ingestion and retrieval design. Environmental readings use MongoDB time-series collections, while transportation retains PostgreSQL tables with sensor/time indexes, as selected earlier. MongoDB provides storage organised for time-series measurements, but restricts updates and schema validation (MongoDB, Inc., n.d.-b, n.d.-c). Queries use bounded periods and preserve metric/unit distinctions. Late arrivals, duplicates and corrections need explicit policies. Transportation time partitioning should be evaluated if sustained growth justifies the additional maintenance.

Service requests remain relational because their assignments and histories require stable relationships. Department ancestry uses a self-referencing hierarchy and recursive SQL; PostgreSQL supports recursive common table expressions (PostgreSQL Global Development Group, n.d.-h). If genuinely variable request attributes emerge, JSONB could supplement typed columns, with validation and indexing (PostgreSQL Global Development Group, n.d.-c). Adding it would require a reviewed schema migration. Hierarchy-cycle checks and controlled recursion prevent invalid organisational paths.

Active behaviour reacts to database changes. We use PostgreSQL triggers for local conditions such as camera classification, department-cycle prevention and completion validation. These mechanisms follow the event-condition-action approach described by Elmasri and Navathe (2016) and execute within the database write path (PostgreSQL Global Development Group, n.d.-g). They support consistent validation, but excessive trigger work increases latency and coupling. External notifications belong to a worker; a transactional outbox would require its own schema and delivery worker.

Emergency logic is a separate responsibility. An evaluation service selects an approved, effective rule version, checks incoming observations and records alerts referencing that version. PostgreSQL preserves the governed conditions and response history, while the service performs evaluation. This separation makes policy changes auditable and supports replay and deduplication. Rule conflicts, stale versions and event bursts require approval controls, idempotency and monitored processing.

Historical planning uses dimensional modelling: shared dimensions describe dates, cities and facilities, while facts retain explicit daily grains. Kimball and Ross (2013) provide the basis for this analytical organisation. Period comparisons and grouped indicators support regional decisions without repeatedly rebuilding meaning from operational joins. Refresh lag, unit compatibility and dimension changes remain risks. A separate analytical database enables distinct reporting management, but independent resource allocation is still required when operational and analytical databases share infrastructure.
